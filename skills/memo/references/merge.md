# Merge Divergent Knowledge

Use when knowledge arrives from another machine, branch, or independent store. A clean Git merge only establishes textual compatibility; different files can still give contradictory guidance.

## Establish The Inputs

Preserve both inputs outside active knowledge before replacing content. Inspect local edits and remote revisions; use a common ancestor when available, but do not invent one for separately created stores. Record the source revisions and a temporary source-to-owner map for coverage checks, not a permanent document registry. Use the configured Spec tools to publish active knowledge; a GitHub binding saves directly to its selected repository. Do not bypass that binding with separate Git operations.

Confirm which projects correspond using their purpose and repository evidence. Directory names are the runtime lookup convention, not proof that differently named stores are unrelated. Reconcile a confirmed rename into one owner and repair routes; do not silently rename a code checkout or combine unrelated projects merely to eliminate duplicates.

## Reconcile Claims, Not Whole Files

Classify each meaningful difference:

- **Equivalent:** keep one clear statement and its useful evidence.
- **Complementary:** retain both in their owning topic or scoped notes.
- **Conditional:** preserve the platform, target host, dependency/version, branch/revision, account, or deployment conditions that explain different behavior.
- **Superseded:** replace current guidance only when a later accepted decision or applicable evidence establishes the change. Keep old reasons only while they affect future judgment, clearly marked historical.
- **Unresolved:** state the competing claims and missing evidence. Do not resolve by timestamp, source machine, or which wording sounds more confident.

Separate where a note was written from where its claim applies. A Mac-authored database runbook may target Linux; a fixture passing on Mac does not establish Linux durability. Native credential mechanisms can differ by OS while sharing one product contract. An obsolete lifecycle workaround is a version change, not automatically a platform difference. Absence on one machine proves neither invalidity nor general applicability.

Keep user decisions, reported observations, source checks, runtime tests, and proposals distinct. Imported past permission to mutate a remote environment does not authorize doing so in this task. Resolve code evidence against the relevant checkout/revision without silently updating the user's working tree. Prefer current native documentation over duplicating contracts; do not claim a fresh runtime verification from a source read.

## Land One Usable Store

Merge shared guidance into topics and isolate conditional detail only where selective retrieval benefits. Split a topic that mixes environments or unrelated responsibilities. INDEX stays a short map; do not concatenate two indexes or keep duplicate machine trees as active authorities.

Check that each input's useful content has a destination or an explicit supersession reason. Repair links after moving files, remove obsolete identity routes and filesystem debris, and check index budgets and unresolved conflict markers. Preserve referenced evidence where it still matters. Recheck live inputs before replacement so concurrent edits are not lost.

Keep snapshots and the temporary merge report outside the active store. Verify the actual Hook reads the merged index for the expected project name; report installation or cross-platform checks that remain unavailable. Update a necessary handoff with the result, then remove completed active routes. Only generalize a recurring merge lesson into Skill guidance; the project's merge history stays outside the product repository.
